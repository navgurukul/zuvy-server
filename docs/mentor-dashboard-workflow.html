Read this first

Four things shape almost everything downstream, so they're worth knowing before the phase-by-phase detail:

  • A mentor's attendance is never captured automatically. There's a real, working webhook-driven attendance pipeline in this codebase — it just only covers regular classes, not mentor sessions. For mentor bookings, joinedAt/leftAt are written by exactly one thing: a manual POST …/attendance call. Nothing else writes them.
  • A session almost never ends up MISSED. Two separate scheduled jobs mark a booking COMPLETED purely by clock time, with no attendance check at all, and one of them runs on every single session-list page load. The MISSED path exists in code but is effectively unreachable.
  • Accepting a reschedule does not move the Zoom meeting. The booking row points at the new slot time; the actual Zoom meeting keeps its original start time. Both participants would show up at the time they were told, and the meeting wouldn't be live.
  • The meeting is created at booking time, not slot-creation time. A mentor opening a slot only reserves a database seat in the Zoom license pool — the real Zoom meeting, with its join link and waiting-room settings, is created inside the student's booking transaction.

03 · Cross-cutting

Zoom license allocation

Runs invisibly inside slot-creation and booking — two layers, both in zoom-license.service.ts.

WhenWhat happensIf it fails
Slot creationA database seat is reserved in license_assignments (sourceType mentor_slot), with a 2-minute cooldown around the slot windowSlot creation fails outright (BadRequestException) if the pool has no free, non-protected seat
Booking (Zoom-side)ensureHostLicensedForWindow makes sure the mentor's actual Zoom account is licensed right now — if not, it finds a "donor" (another licensed, non-protected user with no overlap) and downgrades them to free up a seatNo donor available → booking fails
Slot deletionreleaseMentorSlotAssignment frees the DB seat — the only place this happens—
GapNothing releases a license on cancel, on completion, or for the old slot after a reschedule. Seats only free up once the time window plus cooldown naturally passes, or get reassigned by the donor-downgrade logic for someone else's booking.

06 · Catalogue

Known issues found in this audit

Everything below is a live behavior in the code today, confirmed with file:line evidence — not a hypothetical. Ordered most to least urgent.

Critical High Medium Low / cleanup ✓ RE-VERIFIED independently re-confirmed by a second, direct read of the source — the rest reflect one systematic audit pass that wasn't separately cross-checked line by line
Critical

Mentor attendance has no automatic signal, and MISSED is effectively unreachable

✓ RE-VERIFIED

Attendance is written only by a manual API call. Two separate code paths (the lifecycle cron and a check that runs on every session-list page load) mark a booking COMPLETED by clock time alone, with no attendance check — and the clock-based COMPLETED transition always wins before the no-show check gets a chance to run. Re-read the full cron method directly: the three transitions use the lifecycle value from the original query, not re-fetched between awaits, so MISSED only fires if the job missed the entire slot window.

Critical

Accepting a reschedule doesn't move the Zoom meeting

✓ RE-VERIFIED

The booking points at a new slot time; the Zoom meeting itself still starts at the original time. Both participants are told the new time but the meeting isn't live then. Re-read acceptReschedule end to end (lines 1934–2093): it updates the booking's slot pointer and, if a Google refresh token exists, the Calendar event — there is no zoomService call anywhere in the function.

High

Recordings can stall forever if YOUTUBE_UPLOAD_ENABLED is off

Rows get stuck in PROCESSING_YOUTUBE_UPLOAD indefinitely — the job picker explicitly skips any row in a PROCESSING_* state, and nothing resets one.

High

The recording row enqueued at booking time likely never saves

✓ RE-VERIFIED

enqueueMentorRecordingJob inserts against the global DB connection while the booking row still only exists inside an uncommitted transaction — the foreign key should fail. The error is caught and only logged, so bookings silently fall back to the meeting.ended webhook to create the recording row instead. Re-traced the call site directly: it's invoked via this. (not trx.) at line 1111, inside the still-open transaction that started at line 758 and doesn't close until 1208 — the mechanism is confirmed from the code; it hasn't been watched throwing against a live database.

High

DTO validation is not enforced anywhere in this module

There's no global ValidationPipe and none added locally, so every class-validator decorator on these DTOs (@IsDateString, @MinLength, etc.) is currently decorative. Extra or malformed body fields pass straight through to the service layer.

Medium

No Zoom license is ever released on cancel or completion

Release only happens when a slot itself is deleted. A cancelled or completed booking's seat sits reserved until its time window plus cooldown naturally passes.

Medium

Student feedback's error message is wrong

✓ RE-VERIFIED

It's rejected the instant any feedback already exists (one-shot), but the error text says "locked after 24 hours" — that's actually the separate mentor-side rule. Re-read submitStudentFeedback directly: if (booking.studentFeedback) throw new ForbiddenException('Feedback is locked after 24 hours.') — no time check at all.

Medium

Feedback has no gate on the session having happened

Neither side checks lifecycle state or slot end time — feedback can be submitted before a session starts, or on a cancelled booking.

Medium

Session reminders may double-fire

✓ RE-VERIFIED

The job class handling 24h/1h reminders appears registered as a provider in two different modules. Re-checked directly: app.module.ts imports NewNotificationModule (which provides NotificationJob) and separately lists NotificationJob again in its own top-level providers array — two instances in two injector scopes, each independently scheduling the same crons.

Medium

A pre-upload eligibility check likely silently no-ops for mentor recordings

✓ RE-VERIFIED

It queries an end_time column on the mentor booking table that doesn't exist there — wrapped in a try/catch, so it fails quietly rather than blocking anything. Re-read the raw query directly: SELECT end_time FROM zuvy_mentor_slot_booking — that table's only time fields live on the related slot table, not here.

Low

Recurrence-created slots skip the normal creation gate

Profile completeness, mentorship-enabled-bootcamp membership, and active-Zoom-account checks all run for a single slot but not for RRULE-generated ones.

Low

Dead code: an unused webhook event switch

A second Zoom webhook handler class is registered as a provider but nothing ever calls it — safe to delete, mostly a trap for the next person who greps for "recording.completed" and finds two handlers.

Low

No "fixed window" availability mode

Only a single explicit slot or an RRULE day-repeat exist — nothing auto-splits a block of hours into several bookable slots. (Also flagged separately in the Mentorship Monitoring scoping work.)
